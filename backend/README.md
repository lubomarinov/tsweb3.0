# FexoGold API

Бекендът на злато-обезпечената сметка: FastAPI + SQLAlchemy, Python 3.11+.

> **Демонстрационен проект.** Котировките са симулирани и никакви реални
> средства не се движат.

## Стартиране

```bash
python3 -m venv .venv
.venv/bin/pip install -e ".[dev]"

cp .env.example .env          # и задай FEXOGOLD_SECRET_KEY
.venv/bin/python -m uvicorn app.main:app --reload --port 8000
```

Интерактивна документация: <http://127.0.0.1:8000/docs>

```bash
.venv/bin/python -m pytest    # 31 теста
```

## Защо сървърът е авторитетът

Клиентът има същата счетоводна логика (`src/core/ledger.ts`), но тя служи
само да **покаже** какво ще стане. Този бекенд решава какво наистина става:
сумата се валидира наново, курсът се взима от сървърния поток, а наличността
се чете от базата. Нито едно число от заявката не се приема за вярно.

Двете реализации ползват една и съща формула, за да съвпадат числата, които
клиентът показва, и тези, които сървърът записва — включително посоката на
закръгляне.

## Устройство

```
app/
  domain/        ← чист Python, без база и без FastAPI
    money.py       целочислена аритметика (центове, микрограмове)
    gold.py        GoldPriceSource + симулиран и неподвижен поток
    ledger.py      plan_topup / plan_card_payment / plan_sell
  services.py    ← домейнът среща базата: салда, история, идемпотентност
  models.py      ← таблици; транзакциите са само за добавяне
  routers/       ← HTTP слой
  security.py    ← scrypt пароли, JWT токени
```

Домейнът не знае нищо за HTTP и за базата, затова се тества без да се вдига
сървър или да се създава схема.

## Ендпойнти

| Метод | Път | Какво прави |
|---|---|---|
| `POST` | `/auth/register` | Регистрация; създава и празната сметка |
| `POST` | `/auth/login` | Вход; връща Bearer токен |
| `GET` | `/auth/me` | Текущият потребител |
| `GET` | `/price` | Текуща котировка (публична) |
| `GET` | `/price/history` | История за графики |
| `GET` | `/account` | Салдо, стойност, нереализиран резултат, месечен оборот |
| `GET` | `/account/transactions` | История, най-новото първо, със странициране |
| `POST` | `/account/topup` | Зарежда и купува злато по ask |
| `POST` | `/account/card-payment` | Авторизира плащане; продава злато по bid |
| `POST` | `/account/sell` | Продава злато обратно в евро |

Отказите по бизнес причина връщат **422** с машинно четим `code`
(`insufficient_gold`, `amount_too_small`, `amount_too_large`), за да не
разчита клиентът на текста на съобщението.

## Идемпотентност

Трите финансови ендпойнта приемат хедър `Idempotency-Key`. Клиент, който не е
получил отговор заради загубена мрежа, ще повтори заявката — без този ключ
повторението би било второ плащане. При повторен ключ сървърът връща вече
записаната транзакция:

```bash
curl -X POST localhost:8000/account/card-payment \
  -H "Authorization: Bearer $TOKEN" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"amount": 6280, "merchant": "Супермаркет"}'
```

## Решения, които си струва да се знаят

**Цели числа навсякъде.** Пари в евроцентове, злато в микрограмове. Умножава
се преди делението, за да е делението единствената операция със закръгляне.

**Асиметрично закръгляне.** Купеното злато надолу (платформата не издава
метал, който не е купила), продаденото при плащане нагоре (покритието е
пълно), таксите нагоре до цял цент.

**Оптимистично заключване.** `Account.version` пази две едновременни плащания
по една сметка да не презапишат взаимно салдото.

**`gold_after` на всеки ред.** Книгата се проверява без пресмятане на цялата
история.

**Еднакъв отговор при непознат имейл и грешна парола**, и хеширане дори когато
потребител няма — иначе времето за отговор издава кои имейли съществуват.

## Какво липсва за продукция

KYC и проверка на самоличност; реален ценови доставчик вместо симулирания;
трезор, разпределено съхранение и одит; интеграция с карточен процесор
(авторизация, клиринг, chargeback); Alembic миграции вместо `create_all`;
ограничаване на честотата на заявките; журнал за одит; регулаторно
съответствие и лиценз.
